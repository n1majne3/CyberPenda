# 跑分数据分析口径(已验证)

这些口径在 2026-09 的四轮跑分复盘(docs/tsecbench/RUN-ANALYSIS.md)中
逐条验证过。直接复用,不要重新发明。

## 节奏与吞吐

- **会话级**:每流输出速率 = `total_usage.output / 会话时长`。
  调用率 = `range_call_count / 时长`。只统计时长 ≥1 分钟的会话。
- **并发直方图**:把每个会话的 [first, last] 分钟区间投到逐分钟计数上,
  得平均/中位并发。配额是 3 个靶场容器(编排器不占)。
- **响应级节奏**:`captured_at` 按响应批量落盘,所以 distinct 时间戳的间隔
  ≈ 一次"工具执行 + 下一轮模型"的完整轮次。中位数即轮次长度。

## 斜率测试:预填充 vs 生成/思考

对编排会话,取"快命令之后的单轮延迟"(上一条 bash 不含 sleep、
延迟 3–400s),按当轮 `input + cache_read`(上下文大小)分桶:

- 延迟随上下文陡增、与输出量无关 → 预填充/首字瓶颈。
- 延迟随输出量增长、折算 tok/s 各桶稳定 → 生成瓶颈。
- 混合时可拟合 `延迟 = 固定开销 + 输出/速率`,固定开销即首字税。

已知结论:step-5-preview ≈ 纯生成瓶颈(~40 tok/s);glm-5.3-flash ≈
8s 固定开销 + ~80 tok/s。

## 思考占比

- `thinking` 条目的 char_len 合计 ÷ output token ≈ 2.8(中英混排)时,
  说明思考文本就是 output 的主体,`reasoning=0` 只是未拆字段。
- 口径:执行会话生成字符里 thinking 占比(重思考模型 ≈ 98%)。

## 编排器行为

- sleep 轮询占比:对 bash 命令里的 `sleep <N>` 求和 ÷ 挂钟。
  Pi 接力版曾达 73–79%,是并发饿死的主因之一。
- 派发序列:Agent tool_call 的 args.prompt 里含"题目:<id>"与"预算 N 分钟",
  正则 `题目：([a-z0-9]+-\d+)` 与 `预算 (\d+) 分钟` 可抽出调度时间线。
- 上下文膨胀:编排器逐事件 `usage.input` 的走势;未缓存 input 每调用
  中位数 >5K 说明棒次 prompt 内联过重。

## 得分侧

- score-timeline 按小时聚合得分 → 前置/匀速/收尾形态。
- 家族映射:a=Web(18)、b=多阶段(3)、c=漏洞利用(9)、d=云(6)、
  e1/e2/e3=规避(14)、f1/f2=二进制(13)。矩阵"完成"口径是全对,
  部分得分不算完成;radar 是 flag 口径,两者不矛盾。
- 答错事件在 run_events 的 `answer_wrong` 里,score-timeline 只有对的。

## 常见陷阱

- 分页 `total_pages` 以响应内 `pagination` 为准;榜单接口越界页
  返回与第 1 页相同的 20 条。
- 会话时长 <1 分钟的高频出现时,先查是不是采集粒度假象再下结论。
- 对比两次 run 时,先对齐 Runtime 与棒次预算(Pi 接力 vs Claude Code
  结构差异极大),否则吞吐归因会串。
