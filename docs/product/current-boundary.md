# Current product boundary

Status: current behavior on the project-subtraction branch, 2026-09-08.

Use [CONTEXT.md](../../CONTEXT.md) for domain terms. This document records current
product constraints and routes detailed work to the relevant specification.
It supersedes older descriptions of the retired features listed below.

## Projects, Sessions, and launch

A Project has one current Scope and an explicit Project Kind. Task Launch captures
a matching Task Type and an immutable Scope Snapshot. A later Project Kind
Conversion does not rewrite historical Task Types. Out-of-Scope Facts, Skills,
and Runtime permission settings do not expand authorization.

A Task belongs to a Project. A Session has no Project Scope and owns its separate
conversation and Blackboard. Both use the shared Runtime launch and workspace
surfaces. Sandbox Runner is the default; Host Runner requires explicit activation
and is never an automatic fallback for Sandbox failure.

Direct Launch Selection creates a Runtime Owner-local configuration snapshot.
A Runtime Profile contributes settings only when explicitly selected. Project
Defaults do not select a Profile. Profile and Provider edits do not rewrite
existing snapshots. Resume uses the captured configuration; per-turn model
selection remains separate from Profile selection.

See [owner-local launch configuration](../adr/0031-resolve-launches-with-owner-local-runtime-configuration.md)
and [Task and Session boundaries](../adr/0020-keep-non-project-sessions-separate-while-sharing-runtime-and-blackboard-kernels.md).

## Blackboard

Enabled Blackboard work uses Goal, Step, and Fact through the FGS Runtime Outbox.
New Tasks default to FGS enabled; new Sessions default to Disabled. Launch controls
expose only FGS and Disabled. New enabled owners use the wire value `working_graph`;
new `interactive` input is a compatibility alias. Historical snapshots retain
their original mode, and either enabled value uses FGS on Resume and Continuation.
Skill compatibility treats both enabled values equally and keeps Disabled separate.

Migration 77 updates the Runtime protocol without converting historical records
or deleting Evidence files. Already running processes receive new instructions
only when their Runtime restarts. Entity, Exploration Objective, Attempt, Project
Fact, Finding, Solution, and Evidence Artifact are not additional FGS node types.
Their retained records and reporting interfaces are distinct from the FGS graph.

The Runtime publishes explicit updates. The Harness validates and stores accepted
state and Receipts; it does not infer graph updates from Transcript or schedule
every Runtime action. Local work may be newer than accepted graph state. Recovery
must preserve local work and unconfirmed updates. Fact corrections create new
Facts. A Goal may reopen with a reason; retrying a terminal Step creates a new
Step. Goal completion, Step completion, Task Finish, and Platform verification
are separate outcomes.

Disabled gives the Runtime no Blackboard context or authority. Optional local
Agent-Managed Traces are not parsed into Blackboard knowledge. Reports do not
infer conclusions from Transcript or arbitrary workdir files.

Legacy Intent publication, compilation, and settlement are retired. Retained
records, Receipts, Outbox files, and Evidence stay unchanged. FGS directory
preparation and lifecycle draining remain active.

See the [FGS specification](../specs/fgs-runtime-outbox-protocol.md), including its
implementation-status section, and [ADR 0035](../adr/0035-use-fgs-as-the-blackboard-working-model.md).
Earlier Mode Skill and legacy Intent instructions do not override this boundary.

## Runtime lifecycle and advanced configuration

Task Finish confirms completion after required checks and reconciliation; Stop
interrupts work and leaves it resumable. A later message may resume the same Task,
including a completed Task. Runtime liveness is distinct from Task status and
from reported FGS progress. Accepted Steering has durable, ordered delivery and
must settle explicitly, including after restart.

Runtime Profiles use one on-demand native configuration view generated by the
daemon from the saved Profile, including Custom Config File content. The view is
redacted; Task-specific values are added at launch. The frontend does not create
a separate preview or substitute one after a projection failure. Editing and
Profile Config Import share this view. Save unsaved form changes before import.
Structured fields own their options; raw imports cannot override Managed Config
Keys or store secret-shaped values.

Runtime Non-Interactive Defaults apply to Codex and Claude Code on both Runners.
These defaults remove provider approval prompts; they do not expand Scope or
grant Project Interface authority. Pi uses Global Model Projection, which makes
all global launch-ready Provider credentials available to that Runtime. Codex
and Claude Code do not use that global projection.

Hermes Runtime execution, configuration projection, and image installation are
retired. Existing Profiles, Runtime Configuration Snapshots, and Transcript
records remain readable. New launches and Resume reject Hermes without selecting
a different Runtime. User Runtime homes remain untouched. This supersedes the
Hermes execution and packaging parts of ADR 0026 and ADR 0027.

## Skills and extensions

Runtime Extension discovery uses the local registry and explicit references.
Skills retain managed import. Remote plugin catalog browsing is retired.
Skills are globally reusable and default-enabled, subject to Global and Profile
Skill Opt-Outs. A global opt-out takes precedence without erasing the Profile
choice. Changes affect future projection, not already materialized Runtime state.

CyberPenda has no built-in Blackboard MCP endpoint. External MCP servers remain
explicit Runtime Profile configuration and receive no implicit Blackboard authority.

See [default Skill enablement](../adr/0001-global-default-on-skills.md) and
[global opt-out](../adr/0032-add-global-skill-opt-out.md).

## Retired Challenge Workflow and experiments

Normal Project Challenge Workflow claim, submit, abandon, finalize, Platform
configuration, Task Policy enforcement, and restart recovery are removed.
Challenge history is visible when a Task has retained Attempts or Operations.
Stored states, Evidence, and Task origins remain unchanged. Pending operations
are not replayed; the operator must check unfinished work on the original Platform.
Historical Challenge records do not block Task Finish, and Task Finish does not
confirm Platform completion. New launch controls omit Task Policy.

Reason Task consolidation and approval actions are retired. Legacy health keeps
an empty proposals array for response compatibility. Historical workflow tables
remain stored without execution or replay.

The Assisted experiment launchers are retired. Historical reports and experiment
results remain data, not current execution instructions.

## Hosted evaluation

Hosted evaluation retains its separate Hosted Challenge Client. One evaluation
uses one CTF Challenge Project and Task. The Runtime owns challenge scheduling;
the Hosted Controller bootstraps and observes. The Hosted Task uses Disabled
Blackboard Mode and its Runtime-managed Hosted FGS trace.

The Hosted image supports Codex, Claude Code, and Pi. Hermes is retired. Read the
[Hosted guide](../tsecbench/README.md) and
[troubleshooting guide](../tsecbench/TROUBLESHOOTING.md) for environment variables,
model compatibility, compaction limits, delivery, and acceptance checks.
