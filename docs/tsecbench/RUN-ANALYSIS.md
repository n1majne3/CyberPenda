# TSecBench Hosted 跑分复盘(2026 年 9 月)

本文件记录 CyberPenda 在 TSecBench v1(set_id=4)上四次 Hosted 跑分的量化对比,
给出每种配置的瓶颈判定与证据,并给出下一次实验的行动顺序。
数据来自平台只读 API(`api/v1/leaderboard/*`),原始 JSON 存放在本地
`.tsecbench-analysis/` 目录(未纳入版本管理)。

## 摘要

1. 四次跑分里,只有 16290(deepseek-v4.1-flash + Claude Code)进入 93 分档;
   其余三次(step-5-preview、glm-5.3-flash × 2)聚簇在 63.8–67.5 分。
2. 排行榜公开展示的前 20 名全部使用 deepseek-flash 系模型。CyberPenda 的 93.82
   排第 10,与第 1 名(97.47)差 3.65 分。
3. 63–67 分档不是一种病,是三种:慢流+重思考(step-5)、每轮固定首字延迟
   (glm)、棒次 prompt 膨胀(glm 09-17)。修掉其中一种不能离开该分数档。
4. 93 分档的必要条件是"两个经济指标同时达标":每流有效输出 ≥ 100 tok/s,
   且单轮固定成本(首字延迟 + 未缓存预填充)足够低。16290 在 6 小时内完成
   5,075 次调用,是其余各次的两倍以上。

  `deepseek-v4-flash` 与退役的 `deepseek-v4.1-flash-expires-on-0910` 指向同一

## 模型评测模式(evaluation_type=model)

`agent/19291`(MiniMax-M3,09-17)是一次模型评测跑分。其结构与 agent
跑分不同:

- 每题一个独立 pi 会话,直接给"端到端渗透 + submit-flag 自助提交"的
  完整题面;无编排器、无接力棒、无事实图。
- 会话超时或压缩后,评测以全新上下文重派同一题,直到解出或放弃。
- 本次子集只覆盖 16 题(Web 14 + 漏洞利用 2),16/16 全解(含 a-18,
  该题在 20699 的 agent 跑分中未解),实际工作窗口约 70 分钟,
  消耗 4,580 万 token。

含义:该模式适合做候选模型的快速烟测,但子集未覆盖二进制/规避/云/
多阶段维度,不能替代"每流 ≥100 tok/s、首字 ≤3s"的选型验收指标;
MiniMax-M3 在模型榜(全量 agent 跑分)仅 71.77、多阶段 14,即为例证。
另一直接证据:直连模式每流 11.2 次调用/分钟,而接力模式仅 3.0–3.6,
接力结构对调用率的折损约 3 倍。

## 三种瓶颈与验证方法

### 判定方法:斜率测试

对编排会话,取"快命令(无 sleep)之后的单轮延迟",按当轮上下文大小分桶。
延迟 = 固定开销 + 输出量 / 生成速率。若延迟随上下文陡增,瓶颈是预填充;
若延迟随输出量增长,瓶颈是生成(含思考)。

### step-5-preview:慢流 + 重思考(20699)

- 执行会话生成字符的 98% 是 thinking(样本 877440:213,142 字符思考对
  3,840 字符正文,平均每轮 5,609 字符思考)。
- thinking+正文字符数除以账单 output token = 2.8 字符/token,与文本构成吻合。
  因此思考计入 output,`reasoning=0` 只是 Provider 未拆分字段。
- 斜率测试:上下文 20K→80K+,折算速率稳定在 29–38 tok/s,固定开销趋近于零。
  单轮时间几乎全部用于生成,而其中主体是思考文本。

### glm-5.3-flash:每轮固定首字税(16344)

- 斜率测试:延迟 = 约 8 秒固定 + 输出 / 约 80 tok/s。
  字符流本身不慢;思考很轻(每轮 582 字符)。
- 每轮输出仅约 534 token,固定开销占比过半,有效速率被摊薄到 32 tok/s。

### glm-5.3-flash + 肥棒次(19393)

- 相对 16344:sleep 轮询已修复(79%→约 8%),并发提到 3.91,编排器调用量翻倍。
- 但每次调用的未缓存 input 中位数涨到 6,849 token(背景知识图与事实链内联)。
- 每流调用率从 3.60 降到 2.31 次/分;编排器上下文膨胀到 6,057 万 token。
- 得分 63.81:调度修复的收益被单轮成本上涨抵消。

### 预填充与思考的裁决

"上下文砍半 ≈ 轮次 +70%" 的早期估计作废。斜率测试显示延迟跟随输出量而非
上下文大小,预填充在 20K→80K+ 区间只贡献约 3–7 秒/轮。压上下文仍有助于
减少压缩与未缓存预填充(19393 证明),但它不是 20699 的首要瓶颈。

## 16290 成功配置解剖

- 模型:deepseek-v4.1-flash,每流有效 154 tok/s。
- Runtime:Claude Code。无 12 分钟接力切割;采样其编排器 38 条 bash 命令,
  未发现 sleep 轮询。子代理跑满自然生命周期,编排器即时收割。
- 上下文经济:总 token 3.57 亿中 96.8% 为缓存读,单轮未缓存成本低。
- 调度:第一个小时完成 12,800 分(总分 59%),后 5 小时处理硬尾巴。
- 结束:finished,优雅收尾。

## 行动项(按优先级)

1. 模型选型:Hosted 跑分使用 deepseek-flash 系现役别名(本地 HUB 的
   `deepseek-v4-flash`,窗口 override 已配置:context_window=1,000,000,
   max_output_tokens=131072)。验收指标:每流有效输出 ≥ 100 tok/s,
   单轮固定延迟 ≤ 3 秒。选型时必须实测这两个数,不信任"flash"命名。
2. 编排:Pi 侧保持 19393 之后的低 sleep 占比;评估取消 12 分钟硬切割或
   改为软预算。验收指标:6 小时总调用 ≥ 4,000 次。
3. 思考预算:若必须使用 step 类重思考模型,对执行棒投影低档
   Requested Reasoning Effort,编排器保留高档。
4. 棒次 prompt:背景知识引用走 `pentest-knowledge-lookup` 按需检索,
   不内联大段事实链。验收指标:每次调用未缓存 input ≤ 3,000 token。
5. 收尾保护:结束前 5 分钟停止新派发,只做收割与提交。

## dispatch 系列验收(21034 → 21119 → 21253 → 21416)

薄调度(hosted dispatch-time-injection)四轮实测。21034 为旧 leader.lock
接力版意外基线;21119 为 p2(薄调度首版);21253 为 p3 验证跑(40 分钟);
21416 为 p3 正式跑(完整 6 小时)。

| 指标 | 21034 旧版 | 21119 p2 | 21416 p3 | 设计目标 |
| --- | --- | --- | --- | --- |
| 得分 | 8,900(3.5h 提前收) | 7,100 | **13,650** | ≥17,250 |
| 总 token | ~66M(3.5h) | 481M | **91M** | — |
| 编排器 token 占比 | ~50% | 83.5% | **39.4%** | ≤10% |
| 编排器调用数 | ~200 | 1,142 | **308** | ~150 |
| 每百万 token 得分 | ~135 | 14.8 | **150** | — |
| 结束形态 | 手动 finish | timeout | timeout(挂死 2.5h) | finished |

结论:

1. **结构假设全部成立**:薄调度、退场协议、里程碑接力、事件驱动等待都
   在真实跑分中工作;b 家族(多阶段)在 p2/p3 连续得分(21119 拿下 b-03
   全清,21416 再取 b-01)。
2. **token 经济性数量级改善**:481M → 91M(5.3×),每 token 得分率超过
   旧架构最优值(20699:119 分/M → 150 分/M)。
3. **未达终值的原因不是调度**:21416 在 21:47–21:50 间整体静止
   (编排器最后一次动作是一条阻塞等待,之后 pi 运行时无任何事件),
   平台 6 小时到点才收——约 1/4 窗口被挂死吞掉,按前段得分率折算
   损失约 9,000 分当量。运行时级挂起的心跳监控与自愈是 p4 头号事项。
4. **编排器自进化**:21416 后 61/72 个会话改用"prompt 文件引用"派发
   (Agent 调用只带文件路径,Execute 自行读取),把逐字回显的上下文
   成本从父会话消除——应固化进 SKILL 模板。

p4 待办:运行时心跳与自愈;文件引用派发固化;空闲唤醒继续压缩;
硬题攻坚期(19:13–20:38 出现两段 35–50 分钟无分段)考虑第二梯队并行。
