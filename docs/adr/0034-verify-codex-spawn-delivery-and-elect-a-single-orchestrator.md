# Verify Codex spawn delivery and elect a single orchestrator

TSecBench run 15209 (Codex runtime) lost the orchestrator mid-run. Codex collab `spawn_agent` created child threads but delivered the task message to none of them (5/5 empty-prompt wakes, plus a burst of bootstrap-only sessions). The orphans loaded `ctf-orchestrator`, saw a workdir full of Decide state, and self-appointed as orchestrators — two at once. The real lead ended its turn after its last spawn, and because its children never completed a step, its notification-driven loop never fired again. Budget enforcement died with the lead; the last 100 minutes of the run produced nothing.

Four changes, all inside the hosted `ctf-orchestrator` Skill, no harness change:

1. **First-light identity check.** Every session (lead thread, spawned child, later wake) reads `graph/leader.lock` (single epoch heartbeat, ≤300 s fresh) before claiming the Decide role. A fresh lock held by another session degrades this session to an Execute worker that claims an open step, writes its fact, and exits. A missing or stale lock means takeover, whose first action is the `ledger.tsv` watchdog. This turns an empty-prompt orphan into a worker instead of a second orchestrator, and it gives the run a successor when the lead dies.
2. **Spawn acknowledgement.** Every Execute agent must write its fact skeleton (`graph/facts/NNN-*.md`) within 90 seconds of dispatch. The lead checks the skeleton after each spawn; a missing skeleton counts as a failed delivery and re-dispatches the step (existing 3-retry cap applies).
3. **Turn discipline.** The lead never ends its turn while `ledger.tsv` has unsettled agents: after spawning it stays in `wait_agent` (≤300 s per call) harvest loops. The notification loop is the only thing that can wake the lead, so a lead that ends its turn while workers are live is unreachable by design.
4. **Real-Codex acceptance gate.** `hosted_real_codex_acceptance_test.go` runs the projected skill through a real `codex app-server` against a fake Responses model gateway that groups requests by `prompt_cache_key` (the per-thread identity). It observes whether the spawn message reached the child thread and asserts the acknowledgement loop converges (skeleton exists, leader lock written, task settles live + idle). Codex builds whose tool router rejects `spawn_agent` skip the test with that finding — the gate is the tripwire for the `codex@latest` float allowed by ADR 0026. Local probing found codex 0.153.4 rejects the call under every feature-key combination CyberPenda projects (`multi_agent`, `multi_agent_v2`, `[agents] enabled`), while the image build used by run 15209 routed it; delivery health is therefore a per-build fact the gate records instead of an assumption.

Rejected: harness-side wakeups, keepalives, or subagent scheduling (the Harness only observes subagents; ADR 0018 and ADR 0026 forbid the controller from steering or scheduling); dispatching children through `codex exec` as the primary path (product decision to stay on the Codex built-in multi-agent mechanism; exec remains available for tmux long tasks); pinning the Codex CLI version; mirroring the guards into the generic built-in `ctf-orchestrator` (no upgrade path for seeded daemons, and the hosted contract must not leak into it).
