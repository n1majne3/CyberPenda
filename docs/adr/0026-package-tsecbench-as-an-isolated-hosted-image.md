# Package TSecBench as an isolated hosted image

CyberPenda will enter TSecBench through a separate, self-starting Docker image instead of a new product mode or a changed normal image. The hosted image will run the normal daemon and preserve Project, Task, Runtime, Skill, Blackboard, and policy semantics during execution, while a hosted controller validates environment configuration, starts the evaluation automatically, and observes the Runtime until TSecBench terminates the container. Shared packages may gain additive interfaces, but TSecBench-specific behavior must stay outside normal entrypoints and regression tests must prove that existing application, Sandbox Runner, Host Runner, Challenge Workflow, and startup behavior remain unchanged.

This choice makes the benchmark measure CyberPenda rather than a separate competition Agent. It accepts a larger hosted image and more orchestration work in exchange for behavioral fidelity and isolation from the normal product. One hosted run creates one CTF Challenge Project and one CTF Challenge Task. A Platform-Issued Scope statement in Scope notes authorizes only the ephemeral targets returned for the current evaluation credential; no structured dynamic Scope selector is added. That Task's selected Runtime receives `BENCHMARK_BASE_URL` and `BENCHMARK_TOKEN`, loads a hosted-only TSecBench Skill, and owns the complete platform loop: list, start, solve, optional hint, submit, and close. It may manage between one and three active challenge instances. The Skill explains that hints reduce score and requires sufficient effort before the Runtime requests one.

The hosted Skill documents direct `curl` requests for list, start, hint, submit, and close. The image does not add a TSecBench client binary, structured tool, Challenge Workflow adapter, or controller-side retry policy. The Runtime constructs requests, interprets responses, and decides whether a platform error warrants retry. It closes a challenge immediately after success or explicit abandonment and otherwise owns scheduling within the three-active-challenge platform limit.

The hosted image packages Pi, Codex, and Claude Code. Pi is the default; an environment value may select another packaged Runtime, and startup validation rejects a missing protocol or a Runtime and model-protocol mismatch. Compatibility follows the exact built-in matrix: Codex accepts only `openai_responses`, Claude Code accepts only `anthropic_messages`, and Pi accepts `openai_chat_completions`, `openai_responses`, or `anthropic_messages`. The operator supplies an already converted `.tsecbench.gw` HTTP model URL through the TSecBench environment-variable page; the controller does not transform it. Each Runtime executes as container root through the Container Host Runner and uses only the platform's normal default container capabilities. The image does not depend on TUN, `NET_ADMIN`, a Docker Socket, privileged mode, Docker-in-Docker, or a nested Sandbox Runner. Challenge tools must use normal TCP or HTTP alternatives when an unavailable capability prevents their preferred method. The hosted controller validates configuration, starts the loopback-only daemon, creates and observes the Task, and remains alive until TSecBench forcibly terminates the container. Embedded Web UI resources remain packaged but no daemon port is exposed. The controller does not perform normal Task Finish or infer completion from Runtime idle state. Challenge operations will not be routed through or added to Challenge Workflow or the trusted MCP.

The one-use `BENCHMARK_TOKEN` and a dedicated, revocable evaluation model API key are injected directly into the selected Runtime. Existing persistent Runtime paths do not guarantee exact-value redaction of those values from Events, Transcript source records, or diagnostic state. This internal evaluation-time disclosure risk is accepted; no new persistent Runtime redaction mechanism or local proxy is introduced. The Hosted Controller polls the common Task Transcript API, follows detail links for truncated entries, and emits each retained conversation and tool-result entry as sequence-ordered JSONL. It masks exact values of the two known evaluation credentials before writing standard output. Platform-captured logs may still include flags, target details, attack data, derived secrets, and any sensitive value that is not an exact credential match.

The hosted image uses Kali Rolling but does not copy the existing full CyberPenda Sandbox tool inventory, which is approximately 13 GB in the current environment. It packages a bounded Hosted Tool Baseline and expects the Runtime to implement missing challenge-specific capability with the available shell, language, compiler, and analysis facilities. The image does not rely on runtime package downloads or a second image.

The initial Hosted Tool Baseline includes Pi, Codex, Claude Code, shell and source utilities, Python, Go, C/C++ toolchains, compact binary-debugging tools, pwntools, network utilities, Chromium, and agent-browser. It excludes Ghidra, JADX, Android SDK, large dictionaries, and the full Kali tool set. Delivery builds export and gzip the Docker image exactly as the platform expects and fail unless the resulting archive is below 3 GB.

Bootstrap validates every required environment value, the already-converted gateway URL, and Runtime-protocol compatibility before Project creation or model use. The model URL must be a protocol base URL and must not end in a known operation path such as `/chat/completions`, `/responses`, or `/messages`; the selected Runtime appends that path. Invalid configuration exits nonzero with a non-sensitive error. A failed initial Runtime Turn also exits nonzero without automatic retry, Runtime switching, or waiting for the platform deadline. The Hosted Controller never sends conversation or continuation Turns after creating the initial Task.

Hosted bootstrap is intentionally non-idempotent and non-restartable because the current Project and Task creation interfaces have no idempotency key and an active Runtime cannot resume after daemon restart. Each fresh container process represents one fresh Hosted Evaluation Run. An unexpected process exit fails that run. The hosted PID catches and ignores container termination signals, does not stop the Task or close the daemon, and waits for TSecBench to forcibly terminate the container.

The hosted Runtime receives every normally default-enabled built-in Skill plus a hosted-only TSecBench Skill. Its initial Work Runtime Turn continues until the platform reports every Benchmark Challenge complete or the evaluation enters `invalid_state`; one traversal and subjective no-progress are not completion conditions. Pi's built-in tools execute without permission popups, so bootstrap does not add a synthetic YOLO mode. It deterministically trusts only the projected CyberPenda project resources required for the hosted run so non-interactive project-resource loading cannot depend on an absent prompt.

Runtime CLI packages intentionally install their current releases at build time instead of source-pinned versions. This makes rebuilds from one source revision non-identical, so every produced archive records the exact resolved Pi, Codex, and Claude Code versions. The first delivery targets `linux/amd64`. Its acceptance requires fake-platform API and failure tests, one real TSecBench local-mode run with Pi and `openai_chat_completions` after the deployer connects the TSecBench VPN on the host, and an exported gzip archive below 3 GB. The deployer supplies the gateway base URL, model identifier, and dedicated evaluation API key. Hosted execution does not start or configure a VPN; it uses the isolated network supplied by TSecBench.

The Hosted Delivery Bundle contains the Docker archive, its SHA-256 checksum, a TSecBench page environment-variable template, a local-mode runner, the resolved component inventory, and integration and troubleshooting guidance.

The TSecBench page supplies one Hosted Model Configuration through `CYBERPENDA_RUNTIME`, `CYBERPENDA_MODEL_PROTOCOL`, `CYBERPENDA_MODEL_BASE_URL`, `CYBERPENDA_MODEL`, and `CYBERPENDA_MODEL_API_KEY`. Bootstrap translates these stable inputs into normal Model Provider and Credential Binding inputs. The model protocol must be explicit, the gateway URL must already use the TSecBench form, and invalid or incompatible configuration fails before challenge work. TSecBench's score and completion state are the formal result; container-local Project, Blackboard, Evidence, database, reports, and logs exist only to support execution and diagnosis.
